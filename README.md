## 1. Environment setup

1. **Python:** 3.10 or 3.11 (built and verified on Python 3.11.3).
2. Create and activate a virtual environment, then install dependencies:
   ```bash
   python -m venv .venv
   # Windows:
   .venv\Scripts\activate
   # macOS/Linux:
   source .venv/bin/activate
   pip install -r requirements.txt
   ```
   `requirements.txt` pins: `pandas>=2.2`, `numpy>=1.26`, `pyarrow>=15.0`,
   `pytest>=8.0`. SQLite access uses Python's stdlib `sqlite3` (no extra
   dependency). The feature store is SQLite + parquet only — no mlflow/feast.

3. **Data:** the three raw sources must be at `data/`:
   - `data/customers.csv`
   - `data/transactions.db` (SQLite, table `transactions`)
   - `data/transactions_monthly_agg.parquet`

   Do not edit any of these files. They are provided in the bundle.

All commands below assume the working directory is the project root (this
folder), with the venv active.

## 2. Run the three scripts

### (a) Build training features + populate the feature store
```bash
python scripts/build_training_features.py --as-of 2026-08-01
```
- Runs the single shared `build_features(as_of, ...)` entry point for the full
  1500-customer base.
- Runs `features/quality_checks.py` first; stops (non-zero exit) on any failure.
- Writes `outputs/features_train.parquet` (the training snapshot).
- Registers **every** candidate feature into the feature store
  (`feature_store/registry.db` + `feature_store/values/*.parquet`). Versioned
  features register **every** version: `txn_count_recent` (v1=90, v2=30, v3=180
  days) and `avg_monthly_spend` (v1=6, v2=12 months).
- Regenerates `outputs/artifacts/FEATURE_LINEAGE.md` from the registry.

### (b) Score one or more customers
```bash
python scripts/score_customer.py --customer-id 1 --customer-id 50 --as-of 2026-08-01
```
- Calls the **same** `build_features(as_of, ...)` entry point (scoring path =
  passing `customer_ids`; this is the only difference from training).
- Prints the feature values for each requested customer.
- A nonexistent customer_id raises a clear error and exits non-zero (no silent
  empty result).

### (c) Compare feature versions
```bash
python scripts/compare_feature_versions.py
```
- Loads every registered version of each versioned feature **from the feature
  store** (via `feature_store.store.get_version`), not by recomputing.
- Writes `outputs/artifacts/VERSION_COMPARISON.md`: per-version distribution stats, how many
  customers' values changed between consecutive versions, rank-order
  correlation, and how many customers cross the 75% churn-risk threshold.
- Run this **after** the build script (it reads the registry the build
  populates).

### (d) [optional] Regenerate lineage
```bash
python scripts/generate_lineage.py
```
Regenerates `outputs/artifacts/FEATURE_LINEAGE.md` from `features/schema.py` +
the registry (also done automatically at the end of the build script).

## 3. Run the test suite

```bash
python -m pytest -v
```
`pytest.ini` sets `pythonpath = .` so `features`/`feature_store` imports resolve
with no extra flags. Expected: **51 passed**. The four test files:
- `tests/test_transforms.py` — each feature function in isolation: normal,
  zero-activity, single-record, and time-window-boundary cases.
- `tests/test_parity.py` — train/score parity for a mid-base customer, a
  zero-activity customer, and a multi-customer batch.
- `tests/test_quality_checks.py` — each check fires on deliberately bad input
  and does not false-positive on clean input.
- `tests/test_feature_store.py` — every version independently retrievable,
  `is_latest` = highest version, distinct parquet paths that exist on disk,
  no version overwrite, and re-registering identical parameters is idempotent
  (re-running the build does not duplicate versions).

## 4. Verify parity yourself (optional spot-check)

The parity-mutation check (skill Step 2.1) deliberately reintroduces a
train/score split and confirms `test_parity.py` catches it:
```bash
python _parity_mutation.py
```
This writes/overwrites `outputs/artifacts/PARITY_CHECK.md` and
`outputs/artifacts/parity_mutation_check.txt`. The real `features/build.py` is
never modified (the divergence is in a scratch copy that is deleted after).

To hand-verify one customer across the training snapshot and scoring path:
```bash
python -c "import pandas as pd; from features import build as b; \
t=pd.read_parquet('outputs/features_train.parquet'); s=b.build_features(as_of='2026-08-01', customer_ids=[50]); \
print((t[t.customer_id==50].set_index('customer_id')==s.set_index('customer_id')).all().all())"
# -> True
```

## 5. One-shot runner

`_run_all.py` runs the whole pipeline and saves outputs to `outputs/artifacts/`:
```bash
python _run_all.py
```
It inspects the data, runs pytest, builds the feature store, runs the version
comparison, generates lineage, runs the scoring example and the parity
mutation check, and saves each step's output to `outputs/artifacts/`.

## 6. Outputs

- `outputs/features_train.parquet` — the training feature snapshot.
- `outputs/artifacts/` — all non-code evidence: `FEATURE_LINEAGE.md`,
  `VERSION_COMPARISON.md`, `PARITY_CHECK.md`, `ARTIFACT_NOTES.md`,
  `review_log.md`, saved `pytest_output.txt`, the registry query, the build
  log, and the parity-mutation run.
- `feature_store/registry.db` + `feature_store/values/*.parquet` — the local
  feature store.

## 7. As-of-date control

The entire pipeline runs from a single `as_of` parameter (`2026-08-01` by
default, the day after the latest observed transaction 2026-07-31). It is
threaded into every transform and never hardcoded inside a transform; the only
defaults live in the CLI scripts.
